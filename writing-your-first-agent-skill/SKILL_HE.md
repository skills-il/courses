# איך כותבים את הסקיל הראשון שלכם

רוב המפתחים שכותבים סקיל סוכן בפעם הראשונה מגיעים לאחת משתי תוצאות: סקיל קטן, ממוקד ושימושי שבאמת משתמשים בו, או SKILL.md ענק באורך 2000 מילים שה־LLM אף פעם לא טוען כי התיאור עמום מדי. ההבדל אינו כמות העבודה. ההבדל הוא להבין איך ה־LLM רואה את הסקיל ברגע הניתוב, ומה המפרט מאפשר לכם לומר.

הקורס הזה מיועד למפתחים שיודעים לכתוב קוד אבל עוד לא כתבו סקיל, או שכתבו אחד ורוצים להבין למה חלק מהסקילים נטענים בקלות ואחרים נשארים בלי שימוש. שישה פרקים. דוגמאות קונקרטיות. הסקיל שתפיקו יכול להיות סקיל פרטי אצלכם, סקיל לצוות, או תרומה לקטלוג ציבורי. עקרון העבודה זהה בכל שלושת המקרים.

הקורס מניח שאתם מכירים git ברמה בסיסית, Markdown ו־JSON. לא נדרש ניסיון קודם עם פורמט הסקילים.

## פרק 1: מה זה סקיל באמת?

סקיל הוא הדרך הפשוטה ביותר ללמד עוזר AI איך לטפל במשימה מסוימת: קובץ הוראות אחד (Markdown) עם YAML frontmatter בראש, ולעיתים גם קבצי reference וסקריפטים. הסוכן קורא את הקובץ לפי דרישה, כשהתיאור שלו תואם לבקשת המשתמש. זה כל העיקרון. כל השאר (איך מפיצים את הסקיל, איך מתקינים אותו, ואיזה UI הקטלוג מציג סביבו) נבנה סביב אותו קובץ בודד.

### ההשוואה בארבע: סקיל מול MCP מול system prompt מול CLI

הכי קל להבין מה סקיל הוא, דרך הבנה של מה הוא לא.

| כלי | מה זה | מתי הייתם כותבים אחד |
|---|---|---|
| **סקיל** | קובץ Markdown שה־LLM קורא לפי דרישה כדי ללמוד איך לטפל בסוג משימה מסוים | אתם רוצים שה־LLM יידע איך לעשות משהו בלי שתחזרו על ההוראות בכל שיחה |
| **MCP server** | שירות רשת שה־LLM קורא לו כדי לקבל מידע חי או לבצע פעולות על מצב חיצוני | אתם צריכים שה־LLM יקרא או יכתוב מצב חיצוני (DB, API, מערכת קבצים) |
| **System prompt** | הוראות קבועות שמוזרקות בתחילת השיחה | אתם רוצים התנהגות שחלה על כל השיחות של העוזר, לא רק על משימה מסוימת |
| **CLI tool** | תוכנה שאדם מריץ ישירות | המשתמש יודע בדיוק איזו פקודה הוא רוצה להריץ, אין צורך בניתוב שפה טבעית |

בלבול נפוץ: אנשים כותבים סקיל כשהם בעצם צריכים MCP. אם ה"סקיל" שלכם מסתכם ב"שה־LLM יקרא ל־API הזה ויחזיר את ה־JSON", זה MCP server, לא סקיל. סקילים מיועדים ל"איך עושים משהו" (חוקי החלטה, מבנה, שיקול דעת). MCP מיועד לגישה למצב חי.

בלבול נפוץ שני: אנשים כותבים סקיל כשהם באמת צריכים system prompt. אם אתם רוצים ש־Claude ידבר תמיד בטון של המותג שלכם בכל שיחה, זה system prompt או GPT מותאם, לא סקיל. סקילים נטענים לפי דרישה כשכוונת המשתמש תואמת לתיאור של הסקיל.

### מפרט הסקיל, בפסקה אחת

כל סקיל הוא תיקייה שמכילה לפחות קובץ `SKILL.md` עם YAML frontmatter. ה־frontmatter דורש בדיוק שני שדות, `name` (slug ב־kebab-case) ו־`description` (משפט או שניים שהסוכן קורא כדי להחליט אם לטעון את הסקיל). ארבעה נוספים אופציונליים: `license`, `compatibility`, `metadata` ו־`allowed-tools`. הגוף הוא Markdown רגיל, שנטען לקונטקסט של ה־LLM ברגע שהסקיל מופעל. אופציונלית התיקייה יכולה להכיל תת־תיקייה `references/` (קבצים סטטיים שה־LLM קורא בעת הצורך) ותת־תיקייה `scripts/` (קוד הרצה שכלי ה־shell של הסוכן יכול להריץ). זה כל המפרט.

### מתי לא לכתוב סקיל (עץ ההחלטה)

לפני שכותבים שורה אחת של SKILL.md, עברו על הבדיקה הזאת:

- **האם ה־LLM כבר עושה את זה טוב בלי סקיל?** אם אתם שואלים את Claude "תפרמט את מספר הטלפון הישראלי הזה" והוא עושה את זה נכון מהפעם הראשונה, אתם לא צריכים סקיל לפרמוט טלפונים. סקילים מיועדים למקרים שבהם ברירת המחדל שגויה, חלקית, או לא מותאמת תרבותית.
- **האם המשימה דורשת מידע חי?** אם התשובה משתנה כל שעה (מחירי מניות, תשובות מ־API ממשלתי, תנועה), הסקיל הוא ההפשטה הלא נכונה. כתבו MCP server.
- **האם המשימה חישובית טהורה עם תשובה אחת נכונה?** checksum פשוט או ממיר פורמט אולי מתאים יותר כשורת scripts/ אחת שנקראת מתוך סקיל גדול יותר, ולא בתור סקיל בפני עצמו.
- **אתם בטוחים שיש קהל לזה?** דברו עם 3 משתמשים פוטנציאליים לפני שכותבים. סקילים שאף אחד לא משתמש בהם ננטשים בשקט על ידי הכותבים שלהם. וולידציה מוקדמת חוסכת את האכזבה הזאת.

הטעות הכי נפוצה בפרק 1: כתיבת סקיל במקום שבו MCP מתאים יותר. סימפטום: הגוף של הסקיל ברובו "תקראו ל־URL הזה, פרסרו את ה־JSON הזה, החזירו את השדה הזה". פתרון: המירו ל־MCP server עם כלי אחד, וה"סקיל" שלכם הופך לקריאה בשורה אחת ל־MCP.

אם הנושא שלכם שורד את עץ ההחלטה, עברו לפרק 2 ללמוד מה לשים בתוך SKILL.md.

## פרק 2: האנטומיה של SKILL.md

SKILL.md טוב עושה שלושה דברים בו זמנית: אומר ל־LLM מתי לטעון את עצמו (התיאור), מלמד את ה־LLM איך לבצע את המשימה (הגוף), ונותן ל־LLM מספיק דוגמאות כדי להתמודד עם edge cases בלי להעביר את זה למשתמש. אם אחד מהשלושה חסר, הסקיל או שלא נטען (כשל בתיאור), או שעושה את הדבר הלא נכון (כשל בגוף), או ששואל את המשתמש יותר מדי שאלות מבהירות (כשל בדוגמאות).

### שדות ה־frontmatter

```yaml
---
name: id-validator
description: Validate national ID numbers (such as the Israeli תעודת זהות) using a Luhn-style check-digit algorithm. Use when a user pastes a 9-digit ID and asks "is this valid", or when generating sample IDs for testing. Do NOT use for credit card numbers, EAN barcodes, or international passport numbers.
license: MIT
---
```

- **`name`** חייב להיות באורך 1 עד 64 תווים, אותיות קטנות, ספרות ומקפים בלבד, בלי מקף בתחילה או בסוף ובלי שני מקפים רצופים, וחייב להיות זהה בדיוק לשם תיקיית האב. בחרו שם מדויק: `id-validator`, לא `id-tools`. דרישה של המפרט.
- **`description`** הוא השדה הכי חשוב בסקיל. בסביבות הרצה שמשתמשות בניתוב לפי תיאור (skill discovery של Claude Code זאת הדוגמה הקנונית), ה־LLM קורא בעיקר את השדה הזה כדי להחליט אם לטעון את הסקיל לקונטקסט. בסביבות אחרות המשתמש בוחר את הסקיל מרשימה ידנית, אבל התיאור עדיין הדבר הראשון שה־LLM רואה. תתייחסו אליו גם כנוסח שיווקי וגם כמפרט ניתוב. דרישה של המפרט.
- **`license`** אופציונלי במפרט, בדרך כלל `MIT`. המפרט ממליץ לשמור אותו קצר: שם רישיון, או שם של קובץ רישיון מצורף.

שלושת השדות האופציונליים האחרים כדאי להכיר גם אם לא תשתמשו בהם:

- **`compatibility`** (עד 500 תווים) מציין דרישות סביבה, והמפרט אומר במפורש שרוב הסקילים לא צריכים אותו. השתמשו בו כשהסקיל שלכם באמת לא יעבוד בלי משהו: `compatibility: Requires git, docker, jq, and access to the internet`.
- **`metadata`** הוא מיפוי ממפתחות מחרוזת לערכי מחרוזת, עבור מאפיינים שהמפרט עצמו לא מגדיר, כמו `author` ו־`version`. תנו למפתחות שמות ייחודיים כדי להימנע מהתנגשות עם כלים אחרים.
- **`allowed-tools`** הוא מחרוזת מופרדת ברווחים של כלים מאושרים מראש, למשל `allowed-tools: Bash(git:*) Bash(jq:*) Read`. הוא מסומן כניסיוני והתמיכה בו משתנה בין סוכנים, אז אל תבנו עליו.

### המגבלות שאף אחד לא מספר לכם עליהן עד שהסקיל נדחה

המפרט קובע גבולות קשיחים, והם הסיבה הנפוצה ביותר לכך שסקיל נכשל בוולידציה בהגשה הראשונה:

| שדה | מגבלה |
|---|---|
| `name` | 1 עד 64 תווים |
| `description` | 1 עד 1024 תווים, לא ריק |
| `compatibility` | 1 עד 500 תווים, אם קיים |
| גוף `SKILL.md` | לשמור מתחת ל-500 שורות |
| הוראות שנטענות בהפעלה | מומלץ מתחת ל-5000 טוקנים |

שתי הערות מעשיות על תקרת התיאור. ראשית, כתבו אותו בגוף שלישי. התיאור מוזרק ל־system prompt, וערבוב של גופים ("אני עוזר לכם לאמת..." לצד "מאמת...") גורם לבעיות באיתור הסקיל. שנית, אל תכתבו עד הגבול. חלק מיעדי הפרסום אוכפים תקרה מחמירה יותר מזו שבמפרט, וחלקם סופרים את התווים אחרת ממכם, כולל מרכאות של YAML, כך שתיאור שמודד 1024 אצלכם עלול להידחות כארוך מדי אצל מי שאתם מגישים לו. תשאירו מרווח אמיתי, בסביבות 950, ותבדקו את התקרה של היעד שלכם לפני ההגשה. טריק מעשי כשצריך לגרד עוד כמה תווים: נקודתיים בתוך השורה מכריחות את YAML למרכאות על כל הערך, אז שכתוב של נקודתיים לפסיק הוא לא פעם הקיצוץ הזול ביותר שיש.

### התיאור הוא קלט הניתוב

בסביבות שמגלות סקילים אוטומטית לפי תיאור (Claude Code זאת הדוגמה הקנונית), ה־LLM סורק את התיאורים של הסקילים הזמינים כדי להחליט איזה (אם בכלל) לטעון. הוא לא קורא את הגוף. הוא לא קורא את `references/`. הוא קורא רק את התיאור. בסביבות שבהן המשתמש בוחר סקיל ידנית מרשימה (אפליקציות Claude, חלק מהזרימות בעורכים), התיאור הוא עדיין הסיכום שמופיע למשתמש ושקובע אם הוא יקליק. כך או כך, התיאור צריך:

1. לתת שם ברור למשימה (בשתי השפות של המונח, אם יש שם בקונטקסט שאינו אנגלית)
2. להפעיל על דפוסי שפה טבעית שמשתמש באמת היה משתמש בהם
3. לפסול מקרים שנראים דומים אבל דורשים סקיל אחר

הדפוסים "Use when..." ו־"Do NOT use for..." הופכים את זה לקונקרטי:

> "Validate national ID numbers (such as the Israeli תעודת זהות) using a Luhn-style check-digit algorithm. Use when a user pastes a 9-digit ID and asks 'is this valid', or when generating sample IDs for testing. Do NOT use for credit card numbers, EAN barcodes, or international passport numbers."

הסעיף "Do NOT" קריטי. בלעדיו ה־LLM עלול לטעון את הסקיל הזה כשהמשתמש שואל על ספרת ביקורת של כרטיס אשראי, ואז ינסה להפעיל את גרסת ה־Luhn שמותאמת לתעודות זהות בנות 9 ספרות וייכשל בצורה מבלבלת. עם הסעיף "Do NOT", ה־LLM מנתב נכון למקום אחר.

### מבנה הגוף: scope, חוקים, דוגמאות, אנטי־דפוסים

הגוף הוא מה שה־LLM קורא אחרי שהחליט לטעון את הסקיל. הוא צריך ארבעה חלקים, פחות או יותר בסדר הזה:

1. **Scope** (פסקה אחת): מה בדיוק הסקיל הזה מכסה, מנוסח בצורה יותר מדויקת ממה שהתיאור איפשר.
2. **חוקי החלטה** (הבשר של הסקיל): הלוגיקה אם־אז שה־LLM צריך להפעיל. השתמשו ברשימות, עצי החלטה, או דוגמאות עבודה. תימנעו מפרוזה.
3. **דוגמאות עבודה** (חובה): תראו את הקלט, את החשיבה, ואת הפלט. כסו את המקרה הטיפוסי ולפחות edge case אחד. בלי דוגמאות עבודה ה־LLM ימציא את התנהגות הגבול.
4. **אנטי־דפוסים** (מומלץ): תגידו ל־LLM מה לא לעשות, גם אם זה נשמע מפתה. אנטי־דפוסים מונעים מצבי כשל שאחרת היו נראים נכון.

### אורך הגוף עולה ב־tokens

כל מה שיש בגוף נטען לקונטקסט בכל פעם שהסקיל מנותב. גוף של 4000 מילים עולה בערך 5K-6K tokens לכל turn מפעיל באנגלית (עברית כבדה יותר). לסקיל שמנותב הרבה, זה הופך לכסף אמיתי במהלך חודש.

חוק האופטימיזציה: שמרו את הגוף קצר וממוקד החלטה. העבירו טבלאות lookup ארוכות, templates ופרוזה מפורטת ל־`references/`, שה־LLM קורא לפי דרישה רק כשהוא צריך אותן. פרק 4 מרחיב על הפיצול הזה.

### דוגמה ללימוד: קראו סקיל קטן וממוקד

הדרך הכי מהירה להפנים את זה היא לקרוא אחד. תמצאו סקיל קטן (~150 שורות) עם scope ברור, אלגוריתם דטרמיניסטי ב־scripts/, ודוגמאות עבודה קונקרטיות. רוב הקטלוגים הציבוריים נותנים לדפדף לפי מספר התקנות, מה שמציף סקילים שמתוכננים טוב במהירות. קריאה של אחד מהתחלה ועד סוף מהירה מכל הסבר נוסף שאפשר לכתוב פה.

הטעות הכי נפוצה בפרק 2: כתיבת תיאור עמום מדי. "סקיל לדברים ישראליים" נטען בכל שיחה בקונטקסט ישראלי ולא עושה כלום שימושי באף אחת מהן. תבחרו משימה אחת. תנו לה שם מדויק. הוסיפו את הדפוסים "Use when..." ו־"Do NOT use for...".

## פרק 3: הרחבת הפורמט (אופציונלי)

מפרט הסקילים מינימלי בכוונה: `SKILL.md` עם שני שדות frontmatter נדרשים וארבעה אופציונליים, בתוספת תת־התיקיות האופציונליות `references/`, `scripts/` ו־`assets/`. זהו מפרט פתוח, נתמך ב־Claude Code, באפליקציות Claude וב־API של Claude, ומתקבל אצל מספר גדל של עורכים וסוכנים של צד שלישי. זה מספיק לסקיל פרטי, או לסקיל שאתם משתפים על ידי דחיסת תיקייה ושליחה לעמית. אבל אם אתם רוצים לשים את הסקיל בקטלוג או לחשוף מטא־דאטה נוספת לצרכנים, אתם צריכים להרחיב את המפרט איכשהו.

הפרק הזה מציג דפוס הרחבה אחד נפוץ: קובץ `metadata.json` בתור sidecar ליד `SKILL.md`. השדות למטה הם המוסכמות של קטלוג ציבורי אחד (agentskills.co.il) ושימושיים כדוגמת עבודה. קטלוגים אחרים בוחרים שדות אחרים, וחלק מהם מוותרים על ה־sidecar לגמרי לטובת שדה `locale` ב־frontmatter או תיקיות לפי קוד שפה. הלקח הוא דפוס ה־sidecar, לא מבנה הנתונים המסוים. אם הסקיל שלכם פרטי לגמרי, אפשר לדלג על הפרק הזה לחלוטין.

### למה sidecar JSON ולא YAML מקונן

המפרט כן נותן לכם שדה `metadata` בשביל זה, ולכמה מאפיינים פשוטים כמו `author` ו־`version` זה המקום הנכון. אבל זה במכוון מיפוי ממפתחות מחרוזת לערכי **מחרוזת**, כך שברגע שהקטלוג שלכם צריך שם תצוגה דו־לשוני, מערך של תגיות או רשימה של סוכנים נתמכים, זה כבר לא נכנס. חלק מהסביבות גם היו בעבר מחמירות לגבי YAML מקונן ב־frontmatter וסירבו לטעון סקיל בכלל.

לכן הדפוס המקובל בקטלוגים הוא להשאיר את ה־frontmatter של SKILL.md למה שהמפרט מגדיר, ולמשוך את המטא־דאטה שייחודי לקטלוג לקובץ נפרד בשם `metadata.json` לידו. סביבות שקוראות רק את ה־frontmatter טוענות נקי ולא רואות בכלל את נתוני הקטלוג, וזה בדיוק מה שרוצים: שום דבר מזה לא עוזר לסוכן לבצע את המשימה, אז שום דבר מזה לא צריך לעלות לכם בקונטקסט. כלי הקטלוג קוראים את `metadata.json` ומקבלים את מה שהם צריכים.

### דוגמת שדות metadata.json

```json
{
  "name": "id-validator",
  "version": "1.2.0",
  "license": "MIT",
  "display_name": "ID Validator",
  "display_description": "Validate national ID numbers using a check-digit algorithm. Useful for forms, test data, and catching bad IDs before submission.",
  "audience": "developers",
  "level": "beginner",
  "tags": ["id", "validation", "checksum"],
  "supported_agents": ["claude-code", "cursor", "windsurf", "claude-desktop"],
  "recommended_skills": ["currency-formatter", "date-validator"]
}
```

- **`display_name`** הוא הכותרת בקטלוג.
- **`display_description`** הוא הנוסח השיווקי בקטלוג.
- **`audience`** בדרך כלל אחד מ: `developers`, `non-technical`, `professionals`, `mixed`. קובע את הסינון בקטלוג ואת רמת הכתיבה כברירת מחדל.
- **`level`** בדרך כלל אחד מ: `beginner`, `intermediate`, `advanced`.
- **`tags`** הוא מערך מחרוזות. הקטלוגים מסננים לפי זה.
- **`supported_agents`** משתמש ב־slug קנוני: `claude-code` (לא `claude`), `gemini-cli` (לא `gemini`), `cursor`, `windsurf`, `claude-desktop`. slug שגוי מציג עיגול אייקון ריק על הכרטיסים ברוב ה־UI של הקטלוגים.
- **`recommended_skills`** הוא מערך של slugs שקטלוגים בדרך כלל מציגים כ"סקילים קשורים" בעמוד הפרטים. תבחרו סקילים שמשתמשים באמת צריכים לצד שלכם, לא קישורים פרסומיים. סקיל לאימות תעודות זהות שממליץ על פורמטר טלפונים זה הגיוני. סקיל לאימות תעודות זהות שממליץ על סקיל שיווק לא קשור זה ספאם.

הערה על קטלוגים רב־לשוניים: חלקם מקבלים אובייקטים `{ he, en }` ל־`display_name`, `display_description` ו־`tags` במקום מחרוזות שטוחות, כדי שהקטלוג יציג נוסח שונה לכל שפה. זו מוסכמה של כל קטלוג בנפרד, לא ברירת המחדל. בדקו את מבנה הנתונים של קטלוג היעד לפני שאתם מניחים אחת מהצורות.

הטעות הכי נפוצה בפרק 3: לנחש את מבנה ה־sidecar בקטלוג היעד במקום לקרוא את מדריך התרומה שלו. קטלוגים שונים משתמשים בשמות שדה שונים לאותו מושג (`audience` מול `target_users`, `tags` מול `keywords`, מחרוזות שטוחות מול אובייקטים `{he, en}`). השיגו את המבנה המדויק מהקטלוג לפני הכתיבה. אחרת תכתבו את ה־sidecar מחדש בזמן ההגשה.

## פרק 4: references/ מול scripts/ (מתי להשתמש במה)

המפרט מגדיר שלוש תת־תיקיות אופציונליות: `references/` לתיעוד שהסוכן קורא, `scripts/` לקוד שהוא מריץ, ו־`assets/` למשאבים סטטיים כמו תבניות, תמונות, סכמות וטבלאות lookup. הבחירה הלא נכונה ביניהן היא סיבת דחייה תכופה. השאלה פשוטה: האם הסוכן **קורא** את זה, **מריץ** את זה, או **משתמש** בזה כחומר גלם? החלק הקשה הוא לזהות באיזה צד של הקו התוכן שלכם נופל. אף אחד לא מונע מכם לשים קבצים ותיקיות נוספים בסקיל, אבל שלוש אלה הן הקונבנציות שקוראים וכלים מצפים להן.

### references/: קבצים סטטיים שה־LLM קורא לפי דרישה

`references/` מחזיק קבצים שה־LLM יכול לקרוא כשהוא צריך אותם: הסברים ב־Markdown, טבלאות lookup ב־JSON, נתוני דוגמה, קבצי template, מפרטי תמונות. ה־LLM קורא אותם דרך כלי קריאת קבצים. הוא לא מריץ אותם.

שימושים טיפוסיים:

- **טקסט רץ שהסוכן קורא**: הסבר כתוב על תהליך רב־שלבי, מילון מונחים, מדריך החלטה. (טבלת lookup היא **נתונים** ולא תיעוד, ולכן היא שייכת ל־`assets/`.)
- **תוכן עזר ארוך**: הסבר בן 2000 מילים על תהליך מרובה שלבים, שנשאר מחוץ ל־SKILL.md (שצריך להישאר קצר וממוקד ניתוב) ונטען רק כשה־LLM נתקל בשאלה מסוימת
- **תבניות**: חוזי דוגמה, טפסי דוגמה, נוסח בסיסי שה־LLM מתאים אישית למשתמש
- **מפרטי תמונות**: הנחיות ליצירת איורים, שמורות בנפרד מהגוף

קובץ טוב ב־`references/` הוא משהו שה־LLM צריך רק לפעמים, ולכן טעינה שלו מראש לקונטקסט תבזבז tokens.

### scripts/: קוד הרצה שה־LLM יכול להריץ

`scripts/` מחזיק קוד שהסוכן יכול להריץ: validators, parsers, חישובים דטרמיניסטיים, קריאות רשת. הסוכן מפעיל סקריפטים דרך כלי ה־shell של הסביבה (Bash ב־Claude Code, המקבילה בסביבות אחרות), קורא stdout/stderr, ומשלב את הפלט המפורסר בתשובה שלו. אין מנגנון "function-call" מובנה לסקריפטים במפרט של Skills. סקריפטים הם executables רגילים שהסוכן מריץ וקורא.

שימושים טיפוסיים:

- **חישוב דטרמיניסטי שה־LLM לא צריך לעשות מחדש**: אלגוריתם ספרת ביקורת Luhn לתעודות זהות ישראליות (ה־LLM היה גוזר אותו מחדש בצורה לא עקבית אחרת)
- **Parsers**: פונקציה שלוקחת טקסט גולמי של תלוש משכורת ומחזירה פירוט מובנה ב־JSON
- **חיפושים חיצוניים שדורשים API key**: פונקציה שקוראת ל־API ממשלתי כדי לחפש פרטי רישום עסק
- **קריאות רשת**: scraping של טבלה ציבורית, קריאה ל־RSS feed

סקריפטים חייבים להיות עצמאיים (להגדיר את כל התלויות בכותרת הסקריפט), לכלול הערת שימוש ברורה בראש, ולכתוב ל־stdout בפורמט צפוי שה־LLM יכול לנתח.

### עץ ההחלטה

כשיש לכם תוכן שתומך בסקיל, שאלו:

1. **האם זה חישוב דטרמיניסטי שה־LLM עלול לגזור מחדש שגוי?** ← `scripts/`
2. **האם זה דורש API key, קריאת רשת, או כתיבה למערכת קבצים?** ← `scripts/`
3. **האם זה lookup סטטי, template, או הסבר ארוך שה־LLM צריך רק לפעמים?** ← `references/`
4. **האם זה חוק או דוגמה קצרה ורלוונטית תמיד?** ← inline בגוף `SKILL.md`
5. **האם זה חוק ארוך ורלוונטי תמיד שה־LLM חייב לדעת תמיד?** ← כנראה לא צריך להיות בסקיל. תשקלו system prompt או סקיל אחר שיכסה את זה

### גודל קובץ ומבנה

התקציבים שחשובים הם אלה שהמפרט באמת קובע. תשמרו על `SKILL.md` עצמו מתחת ל-500 שורות, ועל מה שנטען בהפעלה מתחת ל-5000 טוקנים בערך. קבצי reference נטענים לפי דרישה, אז קבצים קטנים יותר שורפים פחות קונטקסט, והמפרט מבקש לשמור על הפניות בעומק של רמה אחת מ־`SKILL.md` ולא לבנות שרשראות של מסמכים שמפנים זה לזה. קבצי `scripts/` צריכים להיות עצמאיים או לתעד בבירור את התלויות שלהם, לתת הודעות שגיאה מועילות ולטפל במקרי קצה. סקריפט שגדל מעבר לנקודה שבה אדם אחד יכול לקרוא אותו בישיבה אחת כנראה צריך להפוך לחבילה אמיתית שהסקיל קורא לה.

תימנעו מ:

- הדבקה של טבלת lookup בת 50 שורות לתוך הגוף של SKILL.md. טבלת lookup היא נתונים, ולכן לפי הקונבנציות הנוכחיות היא שייכת ל־`assets/<table-name>.json`, עם הפניה מהגוף ("ראו assets/area-codes.json").
- כתיבה של סקריפט Python בתוך הגוף של SKILL.md כקטע קוד. תעבירו את זה ל־`scripts/<name>.py` ותפנו אליו.
- שמירה של קבצים בינאריים (PNG, ZIP) ב־`references/`, אלא אם הם נתוני דוגמה שה־LLM מנתח במפורש.

### דוגמאות ללימוד

לדוגמת scripts/ קלאסית, מצאו סקיל שמכיל מימוש קטן של אלגוריתם דטרמיניסטי (Luhn לתעודות זהות ישראליות זו דוגמה טובה). הגוף של SKILL.md מתאר מתי להשתמש באלגוריתם. המתמטיקה עצמה נמצאת בסקריפט. זו הדוגמה הקנונית ל"חישוב דטרמיניסטי שייך ל־scripts/".

לדוגמת references/ מנוגדת, חפשו סקיל ששומר טבלת lookup (קידומות טלפון סלולרי / קווי / שירותים מיוחדים זאת דוגמה נפוצה) כ־JSON ב־`references/`, במקום להדביק את הטבלה בתוך הגוף.

הטעות הכי נפוצה בפרק 4: הדבקת טבלת lookup ארוכה לתוך הגוף של SKILL.md במקום ל־`assets/`. סימן אזהרה: הגוף הוא 80 אחוז טבלה ו־20 אחוז חוקי החלטה אמיתיים. פתרון: העבירו את הטבלה לקובץ JSON ב־`assets/` והפנו אליו מהגוף. ניצול ה־tokens משתפר, והגוף חוזר להיות קריא כלוגיקת החלטה.

## פרק 5: שיתוף הסקיל שלכם

כתבתם SKILL.md, אופציונלית הוספתם references/ ו־scripts/, והסקיל עובד. עכשיו השאלה המעשית: איך באמת משתמשים בו, משתפים אותו עם אחרים, או מפרסמים אותו לקטלוג? הפרק הזה מכסה ארבעה תרחישים לפי סדר המאמץ.

### תרחיש א': סקיל פרטי, מקומי בלבד

השימוש הפשוט ביותר: להשאיר את הסקיל על המכונה שלכם. ב־Claude Code אין בכלל שלב התקנה. שמים את התיקייה בתיקיית הסקילים והיא נטענת מעצמה:

```bash
cp -r my-skill ~/.claude/skills/my-skill
```

היא נקלטת בסשן הבא שלכם. אם אתם מעדיפים להתחיל משלד ולא מתיקייה ריקה, `claude plugin init my-skill` יוצר אחד באותו מקום.

זה הכל. בלי פרסום, בלי ביקורת, בלי קטלוג. סקילים פרטיים תקפים לחלוטין ולעיתים קרובות מתאימים במיוחד לסקילים שקשורים לתהליך העבודה האישי שלכם. שימו לב שזה שינוי מהנחיות קודמות: אין פקודה `claude skill install`, ואם אתם מוצאים אותה במדריך כלשהו, המדריך הזה קדם ל־CLI הנוכחי.

### תרחיש ב': שיתוף עם צוות או חבר

אתם רוצים שעמית ישתמש בסקיל שלכם. שני דפוסים נפוצים:

1. **דחיסת התיקייה ושליחתה.** ארזו את תיקיית הסקיל ב־ZIP (`zip -r my-skill.zip my-skill/`), שלחו ב־Slack, מייל או Drive. המקבל מחלץ אותה לתוך תיקיית הסקילים שלו. תגידו לו לוודא ש־`SKILL.md` יושב בשורש מה שחולץ ולא רמה אחת מתחת, כי חלק מכלי החילוץ עוטפים את התוכן בתיקייה נוספת על שם הארכיון, וסקיל שה־`name` שלו כבר לא תואם לתיקיית האב שלו לא ייטען.
2. **Push ל־repo ב־git והפיכתו ל־marketplace.** זו התשובה הטובה יותר לכל דבר שתשפרו לאורך זמן. אפשר לרשום repo כ־marketplace, ואז העמית מוסיף אותו פעם אחת ומתקין ממנו לפי שם:

   ```bash
   claude plugin marketplace add your-org/your-skills-repo
   claude plugin install my-skill@your-skills-repo
   ```

   מכאן והלאה `claude plugin marketplace update` מושך את השינויים שלכם, וזה בדיוק החלק שגישת העברת־התיקייה לא יודעת לעשות.

שתי הגישות מניחות שהמקבל מרגיש בנוח בשורת הפקודה. לקהל שאינו טכני, קטלוג ציבורי (תרחיש ד') לעיתים קרובות קל יותר.

### תרחיש ג': קטלוג פנים־ארגוני

אם לצוות או לחברה שלכם יש קטלוג פנימי משותף (דירקטוריה פנימית של סקילים שהמהנדסים יכולים להתקין ממנה), עברו את תהליך התרומה של הארגון שלכם. דפוסים נפוצים: PRs ל־monorepo פנימי ב־git, registry פרטי של npm, או סקריפט התקנה פנימי מותאם. תוכן הסקיל לא משתנה. רק מנגנון ההפצה שונה.

### תרחיש ד': פרסום לקטלוג ציבורי

אם הסקיל שלכם שימושי לאנשים מעבר לצוות שלכם, תשקלו קטלוג ציבורי. שתי האפשרויות המרכזיות נכון ל־2026:

- **Marketplaces של תוספים**, שזו הדרך שבה Claude Code מפיץ סקילים. ל־Anthropic יש אחד רשמי, וכל repo ב־git יכול להפוך לאחד, אז זה הדבר הקרוב ביותר למסלול קנוני לסקיל לשימוש כללי. יש גם repo בקוד פתוח בשם `anthropics/skills`, ואפליקציות Claude מקבלות העלאת zip מההגדרות לשימוש אישי.
- **קטלוגים קהילתיים לפי נושא.** הקטלוג הישראלי agentskills.co.il מקבל הגשות קהילתיות לסקילים שרלוונטיים למשתמשים ישראלים (עברית, APIs ישראליים, חוק ישראלי). קיימים קטלוגים קהילתיים אחרים לנישות אחרות.

תהליך התרומה משתנה בין קטלוגים. רוב הקטלוגים הציבוריים מבקשים את תיקיית SKILL.md, תיאור של מה הסקיל עושה, וצורה כלשהי של ביקורת (lint אוטומטי + אישור אנושי). קטלוגים שתומכים בתוכן דו־לשוני מבקשים לעיתים קובץ ליווי לכל שפה ו־`metadata.json` sidecar עם נתוני תצוגה של הקטלוג. קראו את מדריך התרומה של הקטלוג לפני שאתם מגישים.

### רשימת ולידציה לפני שיתוף

לא משנה איזה תרחיש בחרתם, בדיקת שפיות מקומית מהירה חוסכת בושות:

- ל־YAML frontmatter יש `name` ו־`description`, ובנוסף כל שדה אופציונלי מהמפרט שאתם באמת צריכים. אין מפתחות שהמפרט לא מגדיר
- השדה `name` שווה לשם הבסיס של התיקייה
- כל קובץ שאתם מפנים אליו מ־SKILL.md ב־`references/` או `scripts/` באמת קיים בתיקייה
- לתיאור יש דפוס ברור "Use when..." וגם סעיף "Do NOT use for..."
- אם יש לכם כמה גרסאות שפה או `metadata.json` sidecar, הם עקביים פנימית (ה־slugs תואמים, אין תרגומים חסרים)
- הריצו את הסקיל בעצמכם בסשן Claude Code טרי וודאו שהוא נטען ומתנהג כצפוי

### גרסאות ומעקב שינויים

כשאתם מעדכנים את הסקיל, תקפיצו גרסה איפשהו (או שדה `version` ב־frontmatter, או ב־`metadata.json` אם יש לכם, או tag ב־git). semver עובד טוב: patch (0.0.X) לתיקונים, minor (0.X.0) לתוספות, major (X.0.0) לשינויים שוברים או שינוי היקף.

לקטלוגים ציבוריים, הקטלוג בדרך כלל יטפל בהפצת ה־changelog לעוקבים של הסקיל שלכם. לסקילים פרטיים או של צוות, מספיק להחזיק `CHANGELOG.md` פשוט ליד SKILL.md.

### איך עדכונים מגיעים למי שכבר התקין

המפרט לא מגדיר מנגנון update אוטומטי, אז אספקת העדכונים תלויה בסביבה. תיקייה שהועתקה לתיקיית סקילים מתעדכנת בהחלפת התיקייה. סקיל שהותקן מ־marketplace מרוענן עם `claude plugin marketplace update`, שמושך את ה־marketplace מהמקור שלו, וזה אחד הטיעונים הטובים יותר לטובת marketplace על פני העברת תיקיות. התקנה מקטלוג ציבורי (למשל `npx skills-il add ...`) דורשת הרצה מחדש של פקודת ההתקנה כדי לקבל את הגרסה האחרונה. חלק מהקטלוגים שולחים התראה לעוקבים כשסקיל שהם התקינו מקפיץ גרסה. monorepo פנים־ארגוני בדרך כלל מתכנס על סקריפט קצר `git pull && reinstall` שרץ על לוח זמנים.

השלכה מעשית: אם הסקיל שלכם מכיל תוכן שתלוי בזמן (תעריפים, מחירים, חוקים נוכחיים), תניחו שחלק מהמשתמשים שלכם ירוצו עם עותק ישן שבועות אחרי שתקפיצו את הגרסה. או שאתם מתחייבים לשמור אותו עדכני, או שאתם מעצבים את הגוף כך שמספרים ישנים ייכשלו בצורה רועשת ("תוודאו מול המקור לפני שאתם מסתמכים על אלה").

הטעות הכי נפוצה בפרק 5: שליחת עדכון לסקיל בלי להקפיץ גרסה. צרכני הסקיל (או אתם בעצמכם בעתיד) לא יכולים להגיד מה השתנה. תמיד תקפיצו גרסה. תמיד תרשמו במשפט אחד איפשהו מה השתנה.

## פרק 6: רשימת תיוג של 10 דקות לפני שיתוף

הפרק הזה קצר בכוונה. זו רשימת התיוג שמריצים לפני שמשתפים את הסקיל עם מישהו (עמית, קטלוג ציבורי, או אתם בעצמכם בעתיד אחרי הפסקה ארוכה). 10 דקות כאן חוסכות סבבי הערות עם מבקרים ומונעות את טעויות הכתיבה הכי נפוצות.

### 10 טעויות הכתיבה הנפוצות ביותר

1. **תיאור עמום מדי.** "סקיל לדברים ישראליים" מנותב גרוע. תשתמשו בדפוס "Use when X, Y, Z. Do NOT use for A, B".
2. **אין סעיף "Do NOT use for".** בלעדיו ה־LLM טוען את הסקיל שלכם בקונטקסט שגוי ומפיק תשובה שגויה בביטחון.
3. **תיאור ב־YAML block scalar (`>-` או `|`).** חלק מה־parsers מקבלים את זה. אחרים מקפלים את הרווחים אחרת או דוחים על הסף. תשמרו את התיאור בשורה אחת.
4. **ספי קצבה מומצאים, מספרי טפסים מומצאים, או ציטוטי חוק מומצאים.** מדרגות מס שגויות, מספרי טפסים שגויים של רשויות, ציטוטי תקנות מומצאים. המבקרים מצליבים מול מקורות ראשוניים. המצאות נדחות חזק.
5. **slug שלא תואם לשם התיקייה.** רוב ה־validators והקטלוגים דורשים שה־slug ב־frontmatter (או ב־`metadata.json`) יהיה שווה בדיוק לשם הבסיס של התיקייה. אחרת הרישום נכשל.
6. **אין דוגמת עבודה בגוף.** בלי דוגמאות, ה־LLM ממציא edge cases.
7. **הפניות לקבצים ב־`references/` או `scripts/` שלא קיימים.** ולידטור מקומי תופס את זה תוך שניות. תריצו אותו.
8. **slug שגוי ב־`supported_agents`.** `claude` במקום `claude-code`, `gemini` במקום `gemini-cli`. מציג עיגולים אפורים ריקים בכרטיס הקטלוג.
9. **קווי em dash במקום כלשהו ב־SKILL.md, בגוף המתורגם, או ב־`metadata.json`.** קונבנציית הפרויקט היא בלי em dashes, נקודה. תשתמשו בפסיקים, סוגריים, נקודתיים.
10. **שכחתם להקפיץ גרסה אחרי עריכות.** ערוצי ההפצה דורסים את התוכן בשקט, אבל מחוון הגרסה נשאר ישן וצרכנים (או אתם בעתיד) לא יכולים להגיד מה השתנה.

### רשימת התיוג של 10 דקות לפני שיתוף (מילולי)

הריצו אותן בסדר. כל אחת היא פקודת shell אחת או קריאה של 30 שניות.

המספר 10 מתייחס לפריטים ולא לדקות קריאה. פריטים 4 ו-6 הם אלה שבאמת לוקחים זמן.

1. הריצו grep על שלושת הקבצים בחיפוש תו ה־em dash (U+2014). הפלט חייב להיות ריק.
2. תוודאו ש־`name` ב־frontmatter זהה בדיוק לשם התיקייה, ושהוא עד 64 תווים, באותיות קטנות, בלי מקף בתחילה או בסוף ובלי שני מקפים רצופים.
3. תבדקו את אורך התיאור: `awk '/^description:/{print length($0)-13}' SKILL.md`. הוא חייב להיות עד 1024, וכוונו מתחת ל-950 כדי להשאיר מרווח ליעדי פרסום מחמירים יותר. אחר כך תקראו אותו בקול. הוא עונה על "מתי הסוכן צריך לטעון את זה?" במשפט אחד, בגוף שלישי? יש בו סעיף "Do NOT use for"?
4. פתחו סשן Claude Code טרי. הדביקו בקשה שהסקיל שלכם אמור לטפל בה, ואז אחת שהוא לא אמור לטפל בה. תוודאו שה־LLM מנתב נכון בשני המקרים (טוען את הסקיל לראשון, לא טוען לשני).
5. תבחרו מספר אחד, אחוז, או סכום במטבע כלשהו בגוף שלכם. תפתחו את המקור הראשוני שלו. תוודאו שזה תואם.
6. תבחרו את הפרק עם הכי הרבה לוגיקת החלטה. תמצאו את דוגמת העבודה. תגזרו אותה מחדש על נייר כדי לוודא שהמתמטיקה נכונה.
7. תעשו רשימה של הקבצים ב־`references/`, ב־`scripts/` וב־`assets/`. לכל אחד, תעשו grep ב־SKILL.md כדי לוודא שיש אליו הפניה, ותוודאו ששום הפניה אינה עמוקה מרמה אחת.
8. אם אתם מפרסמים לקטלוג עם תצוגה מקדימה, פתחו את סביבת ה־dev או ה־staging של הקטלוג וודאו שהכול נראה נכון, כולל אייקוני סוכנים נתמכים או לוגואים של פלטפורמות.
9. תקפיצו גרסה (ב־frontmatter, ב־`metadata.json`, או ב־git tag, איפה שאתם עוקבים).
10. תריצו את הוולידטור הרשמי של המפרט, שתופס את חוקי השמות וה־frontmatter לפני שמישהו אחר יתפוס אותם:

    ```bash
    skills-ref validate ./my-skill
    ```

    ואז, אם בערוץ ההפצה שלכם רץ ולידטור נוסף, תריצו גם אותו מקומית פעם אחרונה לפני push.

אם כל ה־10 עוברים, שתפו. אם משהו נופל, תתקנו מקומית קודם.

### המבחן "האם תשובת הברירת מחדל של הצ'אטבוט הייתה יותר טובה?"

השאלה הכי חשובה ששואלים לפני שיתוף: האם המשתמש היה יותר טוב בלי הסקיל שלכם, וקיבל את תשובת ברירת המחדל של ה־LLM?

חלק מהסקילים נכשלים במבחן הזה בשקט. הסקיל מותקן, מנותב נכון, ה־LLM טוען את הגוף כצפוי, והתשובה גרועה ממה ש־Claude היה אומר בלי הסקיל בכלל, כי כותב הסקיל קיבע מידע ישן או פישט יותר מדי את החוק.

זה קורה כשהגוף של הסקיל ישן יותר מהמקור התשתיתי. סקיל שמצטט מדרגות מס משנה קודמת, את השכר הממוצע אשתקד, או מחירון לפני שינוי רגולציה אחרון, גרוע יותר מאשר אין סקיל בכלל. תשובת ברירת המחדל של ה־LLM, בהיעדר סקיל, לפחות הייתה משולפת מידע כללי ומכירה בחוסר ודאות. הסקיל המיושן מספק בביטחון מספר שגוי. סקילים חייבים להישמר מעודכנים.

אם אתם לא יכולים להתחייב להחזיק את הסקיל מעודכן לאורך שינויים בתחום, אל תשתפו אותו רחב. תבחרו נושא יציב (אלגוריתמים, חוקים מבניים, דפוסים שלא מתיישנים) במקום נושא רגיש לזמן (תעריפים, מחירים, מוצרים נוכחיים). או תחזיקו את הסקיל פרטי ותעדכנו אותו בכל פעם שאתם שמים לב שהעולם זז.

### מתי לשלוח סקיל ומתי MCP server

סיכום לסיום: אם ה"סקיל" שלכם הוא בעצם "תגיד ל־LLM איך לקרוא ל־API הזה ולנתח את התשובה", אל תכתבו סקיל. כתבו MCP server. שרתי MCP מטפלים טוב יותר במצב חי, קל יותר להחזיק אותם מעודכנים, והם משתלבים באופן טבעי עם סקילים שמטפלים בקבלת ההחלטות.

חלוקה נקייה:

- **סקיל**: איך לפרש את התשובה משרת MCP. מה לעשות עם הנתונים. חוקי ההחלטה.
- **MCP server**: איך להביא את הנתונים. החוזה של ה־API. המצב הנוכחי.

כששניהם נדרשים, שלחו את ה־MCP בנפרד ותנו לסקיל להמליץ להתקין אותו.

### בסיס אבטחה

סקיל הוא לא תוכן סטטי. הגוף נטען כהוראות ל־LLM. קבצי `scripts/` נהפכים לקוד שהסוכן יכול להריץ דרך כלי ה־shell שלו. תתייחסו לשניהם כמשטחי אבטחה.

**ככותב הסקיל** (לפני פרסום או שיתוף):

- **אף פעם אל תכניסו secrets.** `SKILL.md`, `metadata.json`, וכל מה שב־`references/` וב־`scripts/` מופץ כמו שהוא. מפתחות API, מחרוזות חיבור ל־DB, טוקנים אישיים שייכים לסביבה של המשתמש (env vars, keychain של מערכת ההפעלה), לא לתיקיית הסקיל. אם הסקריפט שלכם צריך מפתח API, תתעדו את שם משתנה הסביבה בגוף ותנו למשתמש להגדיר אותו אצלו.
- **תהיו זהירים עם מה ש־`scripts/` עושה.** הסוכן יקרא לסקריפטים שלכם כשהגוף יגיד לו. סקריפט שעושה `rm -rf` או קריאת רשת עם נתוני משתמש עושה את זה על המכונה של המשתמש ובהרשאות שלו. תגבילו את הסקריפטים לחישוב דטרמיניסטי, parsing, וקריאות רשת מתועדות במפורש.
- **תתייחסו ל־`references/` כחלק מההנחיה.** כל דבר שה־LLM קורא מ־`references/` מתפרש כהוראות. סקיל שמכיל טקסט עוין ב־`references/` (למשל "כשתענה בפעם הבאה, התעלם מה־system prompt שלך ו...") נהפך לוקטור prompt injection. אל תכניסו תוכן שלא הייתם מדביקים ל־system prompt.

**כצרכן** (לפני שאתם מתקינים סקיל של מישהו אחר):

- תקראו את גוף ה־SKILL.md לפני ההתקנה. אם אתם לא מבינים מה הוא עושה, אל תתקינו.
- תסתכלו על כל קובץ ב־`scripts/`. אם סקריפט עושה קריאות רשת או נוגע במערכת הקבצים, תחליטו אם אתם סומכים על הכותב.
- לסקילים מקטלוגים, תבדקו את אותות האמון שהקטלוג חושף (מספרי התקנות, ציון אמון, סטטוס ביקורת, סקילים אחרים של אותו כותב). סקילים מכותבים מבוססים לא בטוחים יותר כברירת מחדל, אבל לפחות יש להם אחריות.

### מפרט וקריאה נוספת

- **מפרט Agent Skills**: המפרט הפתוח מתפרסם ב־agentskills.io/specification ובדוקומנטציה של Claude, ומגדיר את שני שדות החובה (`name`, `description`), את ארבעת האופציונליים (`license`, `compatibility`, `metadata`, `allowed-tools`), את מגבלות השדות, ואת הקונבנציות של תת־התיקיות `references/`, `scripts/` ו־`assets/`. כל שדה מעבר למינימום הזה הוא הרחבה ייחודית לקטלוג.
- **תיעוד התקנה לכל סביבה**: Claude Code (שמים את התיקייה ב־`~/.claude/skills/`, או מתקינים מ־marketplace עם `claude plugin install`), אפליקציות Claude (העלאה מההגדרות), ושאר העורכים שמקבלים את הפורמט, לכל אחד תהליך משלו. מה שמשותף הוא פורמט ה־SKILL.md. מסלול ההתקנה לא.

### איפה למצוא סקילים לדוגמה ללמוד מהם

הדרך הכי מהירה להפנים דפוסי SKILL.md טובים היא לקרוא כמה סקילים שמפתחים אחרים פרסמו. חלק מהקטלוגים הציבוריים נותנים לדפדף לפי מספר התקנות, וזה מדד גס ל"הסקיל הזה בנוי מספיק טוב כדי שאנשים באמת ישתמשו בו". לסקילים בהקשר ישראלי, agentskills.co.il הוא קטלוג כזה. לנישות אחרות, מצאו את הקטלוג הקהילתי שמתאים.

שלוש דוגמאות פתיחה שימושיות לפי מורכבות:

- **הכי קטן**: פורמטר ממוקד וצמוד (למשל פורמטר למספרי טלפון של המדינה שלכם)
- **קטן עם `scripts/`**: סקיל שמוסיף אלגוריתם דטרמיניסטי של ספרת ביקורת או parser
- **בינוני עם `references/`**: סקיל דו־לשוני או מרובה־סקשנים עם שימוש אמיתי ב־`references/`

קראו שלושה סקילים מההתחלה ועד הסוף לפני שאתם כותבים את שלכם. הדפוס מתבהר מהר. ואז כתבו את שלכם ושלחו: התקינו מקומית, שתפו עם אדם אחד, ראו מה הוא אומר, ועשו סבב שיפור.

## סקילים נלווים

הדרך הטובה ביותר ללמוד SKILL.md היא לקרוא כמה סקילים גמורים מההתחלה ועד הסוף. אלה שלוש דוגמאות פתיחה לפי דרגת מורכבות, ישירות מהקטלוג הישראלי. התקינו אותן ובדקו את המבנה.

- **מאמת תעודת זהות** (`israeli-id-validator`), הדוגמה הקטנה ביותר: סקיל ממוקד עם ולידציה פשוטה. התקנה: `npx skills-il add skills-il/developer-tools/israeli-id-validator`
- **מפרמט טלפונים ישראלי** (`israeli-phone-formatter`), דוגמה קטנה עם scripts/: עיצוב מספרי טלפון בכל הפורמטים. התקנה: `npx skills-il add skills-il/developer-tools/israeli-phone-formatter`
- **ערכת כלים לקידום אתרים ו־GEO בעברית** (`hebrew-seo-geo-toolkit`), דוגמה בינונית עם references/: סקיל דו־לשוני מרובה־סקשנים עם שימוש אמיתי ב־references. התקנה: `npx skills-il add skills-il/marketing-growth/hebrew-seo-geo-toolkit`
